### 2026-10-05 — Device approval

- Final behavior: Each browser has to be approved once. An unknown browser gets a random device key in an HttpOnly, SameSite=Strict cookie and shows a six-character code. Every approved device gets a **New device** card with the browser kind and the Tailscale machine name, plus a chime. The card doesn't show the code: approving it means typing the code from the new device's screen. The API never returns codes, except to the waiting browser itself, so a request someone else made can't be approved by tapping through it. The first device is approved from the host with `npm run approve`, which asks for the code and calls the running server using `~/.agentdeck/host-key` (mode 0600). `PASSWORD`, if set, also approves a browser, with at most five wrong tries per address in ten minutes. Approved devices are kept in `~/.agentdeck/devices.json` (0600) by key hash, so restarts keep them. **Devices** in the sidebar footer lists them, and **Remove** closes that device's live stream at once. Its pages then say it was removed, and **Ask again** requests approval anew. Requests lapse after ten minutes, and at most five wait at once. All API calls are refused when `Sec-Fetch-Site` (or `Origin`) shows another site or port. Requests under any name other than an IP address, `localhost` or this machine's MagicDNS name (full or short) are refused too, which stops DNS rebinding. The MagicDNS name is looked up again, at most once a minute, if Tailscale wasn't up at startup. `ALLOWED_HOSTS` adds other names. This replaces the in-memory password sessions, which ended at every restart. Without `PASSWORD`, any browser on the tailnet, and any web page open on one of its devices, could run agents.
- Verification: `node --check` on all changed files. A test server with a temporary home was checked with curl. Unapproved API calls got 401. For `Host`, IPs, `localhost`, the MagicDNS name (full, short, upper case, trailing dot) and an `ALLOWED_HOSTS` entry passed. `yangs-mac-mini.local`, `evil.local`, `evil`, another `*.ts.net` name and `rebind.evil.com` got 403. `/api/devices` listed requests without codes. A wrong code for a card was refused and the request kept waiting. A lowercase code with a space approved it, and a stale request id was refused. `Sec-Fetch-Site: same-site`, a foreign `Origin` and `Origin: null` got 403. Repeated asks kept one code, and `tailscale whois` named the machine. The CLI listed requests without codes and printed instructions when not on a terminal. In a real pseudo-terminal it approved a typed code, refused a wrong one and cancelled on Ctrl+D. It also explained when the server wasn't running. Also checked: deny then ask again, approval from another device, the sixth wrong password refused, the sixth waiting request refused, and approvals kept across a restart. Removal closed the removed device's event stream while the other device received `devices_changed`. Headless Chrome (desktop and iPhone 13) went through these steps: password sign-in; a live request card that didn't contain the code; a wrong code shown as an error on the card; a half-typed code kept when a second request arrived; denying the second; approving the first by typing its code in lowercase and pressing Enter, which reloaded it into the app; the Devices dialog; removing the phone; and removing itself. There were no page errors. Screenshots checked, including the card at phone width.
- Remaining limitations: Waiting requests and denials are kept in memory, so a restart forgets them (approved devices stay). Anyone on the tailnet can keep five requests waiting and so block new approvals for ten minutes at a time, though the password and existing devices still work. Behind `tailscale serve`, every request comes from localhost, so the wrong-password limit applies to all clients together and the machine name depends on `X-Forwarded-For`. A home-screen web app on iOS needs its own approval. An approved device's cookie works from any machine, so someone who copies it off a device gets in until that device is removed.

### 2026-10-05 — Forking a conversation

- Final behavior: Every message you sent carries a fork control, shown on hover once the chat has a stored session and no turn is running. It branches the conversation: `POST /api/fork` has the agent copy it through the end of that exchange into a new session, which the browser then opens with a "Forked from …" line; forking from the last message copies the whole conversation. Branches are the agents' own sessions (Claude Code's `forkSession` with `upToMessageId`, Codex's `thread/fork` with `lastTurnId`, opencode's `POST /session/{id}/fork` with `before`), so they resume in a terminal too, and each one inherits the model, effort, mode and tags of the chat it came from. `fork?()` is a new optional method on the backend interface and `fork` a new flag in an agent's options.
- Verification: `node --check` on every changed file. Claude: forks of a copied three-turn transcript, in a temporary `CLAUDE_CONFIG_DIR`, kept one, two and all three turns and reported `whole` only for the last; through the API the branch inherited the tag and the model/effort record, and the sidecar files showed both.
